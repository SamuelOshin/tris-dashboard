# TRIS v2.0 — Transferability Test (Environment A and Environment B)

Decision D2: show that the manufacturing pipeline is not built around one company's data. A second,
genuinely different environment is run through the **same** detection, forecasting, exposure, risk-scoring
and validation code, with nothing changed in that code. What differs between the two environments is
configuration only: the column mapping used to read each file and the dataset name.

Test: `backend/tests/modules/v1/test_transferability.py` (raw output in `docs/evidence/ticket-12/`).
Data generator: `backend/app/scripts/environment_b.py` (deterministic, fixed seed). Files:
`docs/samples/environment_b/`.

## The two environments

| | Environment A | Environment B |
|:---|:---|:---|
| Business | Solar-panel manufacturer | Precision components and fasteners (industrial products) |
| Source | Seven separate CSV files (`docs/samples/erp_mapping/generic_*.csv`) | One Excel workbook, one sheet per table (`environment_b_industrial.xlsx`) |
| Column names | Close to the canonical names (`material_id`, `unit_price`, `po_number`, …); the preview matches them with no help | Its own names (`Part No`, `PO Line`, `Cost Each`, `Qty Ordered`, `Per Assembly`, `Meas Unit`, `Delivered On Time`, …). **No Generic, SAP-style or Dynamics-style preset matches any of them** (tested for every sheet) |
| Dates and numbers | ISO dates, plain numbers | `31.01.2025` day-first dates, `20250131` months, quantities written with thousands separators (`12,500`) |
| Identifiers | `SOL-GLASS-32`, `PANEL-60C`, `SUP-001` | `4410-0231`, `GBX-100`, `V-HX-01` (no overlap with A) |
| Categories | Glass, Metals, Polymers, Electrical, Cells | Fasteners, Bearings, Machined Parts, Springs, Seals, Castings (no overlap) |
| Purchasing pattern | Exactly one purchase line per material per month, 24 months, USD | One to three lines a month, 36 months, euro and dollar prices, some missing months, one part with only 9 months of history |
| Price behaviour | Synthetic solar-component prices | A steel-price surge in 2024 with different sensitivity per part, a tariff step on one supplier from 2025, slowly rising seal prices, stable bearings |
| Size | 6 materials, 144 purchase lines | 12 materials, 595 purchase lines |

Environment B is generated by us, so it is "different" in structure, naming, cadence and price behaviour,
not independent real-world data. Both environments are synthetic.

## What is configuration and what is core

**Configuration (differs per environment):**

1. The column mapping, set per file in the ERP/BOM mapping screen (or saved as a mapping profile):
   Environment A used the suggestions the preview made on its own; Environment B's mapping is written out
   in `ENVIRONMENT_B_MAPPINGS` (sheet → table → `{canonical field: raw column}`), because nothing in it is
   recognised.
2. The dataset name given to each import (`Synthetic Environment A` / `Synthetic Environment B`), which
   keeps the two apart in one database.
3. The supplier directory, which both environments' suppliers are loaded into the same way (it is the v1.4
   supplier master; the mapping engine only refers to it).

**Core logic (identical, untouched):** data loading, price series, detection signals, forecasting engine
and model selection, financial exposure, risk scoring and weights, the validation protocol and metrics.
No settings differed between the two validation runs: the same method version (`1.2`),
forecast engine version, risk method and risk weights version (`1`), and default thresholds.
`git diff f924989 -- backend/app` shows no change to any existing file for this ticket: the only new
application file is the data generator, which the pipeline never imports.

## How "no environment-specific branching" is checked

`test_the_same_pipeline_code_handles_both_environments_without_branching` (required) imports both
environments through the ordinary import API, runs detection, forecasting (every material), exposure, risk scoring and a
validation run through the HTTP API for each, and records which functions of the pipeline code ran:

- every pipeline file that ran for one environment ran for the other, and no import/mapping code ran during the analysis;
- the entry points of each stage (`compute_results`, `run_horizon`, `baseline_exposure`, `score_material`,
  `freeze_cutoff`) ran for both;
- 185 functions ran for A and 184 for B. The only ones that ran for one environment alone are state- or
  data-driven helpers (an empty-result builder, "no stored forecast" for exposure, the lock taken only by the first
  scoring run in a database, and the loop bodies of one BOM check), listed in the test: none refers to either environment;
- each stage produced real output for each environment (no empty or fabricated results).

**What this does and does not prove.** The function trace shows the two environments run the same code; it cannot see a
branch *inside* a shared function. So two further tests read the source of every pipeline file under `service/`
(everything except the file-reading and mapping files): no string literal names a part, vendor, assembly, category,
dataset or raw column of either environment, and no code special-cases a dataset, material, supplier, category, currency or unit
(comparison with a fixed value or list, `startswith`/`endswith` on an identifier, a fixed table or `match` keyed by one).
The scanners are tested on code that special-cases each of those ways (they flag it) and on ordinary code (they do not).
They are a tripwire for the plausible ways of special-casing a dataset, **not a proof**: they do not read routes or models, and a determined
or unusual construction would pass. Read together with the unchanged-code evidence above, they support "no environment-specific logic was
added or found", not "none could exist".
A further test checks that B really is different from A (preset matches, identifiers, categories, cadence, currencies, format).

## Side-by-side validation results (same settings, method 1.2, default thresholds)

Run `VAL-62C841802F` (A) and `VAL-DFA07BFDC6` (B) on a fresh database; one cutoff per month from the first
date with 13 months of history to the last whose holdout month is complete (A: 10 cutoffs, B: 22).
The warning threshold is the High band of the risk weights (50).

### What the side-by-side shows

1. **The pipeline carried over without a code change.** Everything that worked for A worked for B, including
   an Excel workbook, day-first dates, thousands separators, two currencies, several purchase lines a month and
   missing months. Gaps and thin histories were withheld with a reason, not filled in.
2. **The forecast result is the same as in Environment A: no evidence of skill over "the price stays the same".**
   In B the forecasts were closer than the naive forecast in 19% of the 30-day cases
   and further in 31%; direction was right about half the time. The typical error is lower in B, but the comparison with the naive forecast is what matters.
3. **The risk warning did not work on B.** B had 4 risk-event cases at the 30-day outlook and 21 at 90 days (the same price rises overlap between the two outlooks and between neighbouring cutoffs, so these are not independent events); the warning at the default level caught none of them
   and raised 4 and 4 false alarms. In A it caught a few (1 of 8 and 1 of 12). The weights were not tuned for either environment; the honest reading is that the risk score, as weighted, is
   not a reliable early warning on this synthetic data in either environment.
4. Transfer here means **the same method runs and reports honestly on a different dataset**, not that the forecasts or warnings are
   accurate on it. This is the same conclusion as `VALIDATION_RESULTS.md`.

## What this does not show

- **Environment A is already close to the canonical schema**: its column names are essentially the canonical ones and the preview matches them
  with no help. So A against B shows the engine and pipeline handle a file with *foreign names, formats and structure* (B); it does not show a move
  between two differently named ERP exports. The instruction's optional step, one SAP-style and one Dynamics-style layout across the two environments,
  was **not** done for B (A has SAP-style and Dynamics-style samples from Ticket 5; B uses a custom mapping).
- The import and pipeline have assumptions a real second company could break; the tests do not exercise them:
  quantities and units are carried but **never converted** (a BOM in grams against purchases priced per kilogram would give wrong figures
  without an error); on-time delivery must be given as a fraction 0 to 1; dates must be ISO, `yyyymmdd`, `dd.mm.yyyy` or `mm/dd/yyyy`
  (`31/01/2025` is rejected, and an ambiguous slash date is read month first); prices are compared within one currency (no conversion).

## Limitations

- Both environments are synthetic; B was generated for this test and mirrors our own assumptions about a
  fastener business. A real second company would test the mapping more severely.
- Few materials (6 and 12) and overlapping cutoffs; the rates are indicative only (see `VALIDATION_PROTOCOL.md`).
- B has few risk-event cases (4 and 21, overlapping), so its precision and recall carry very little information.
- The supplier directory is loaded outside the mapping engine for both environments (v1.4 master data).
- SAP-style and Dynamics-style layouts are demonstrated on Environment A's samples (`sap_style_*`, `dynamics_style_*`,
  Ticket 5). Environment B uses a custom mapping; it was not also produced in an SAP or Dynamics layout.
- The Validation page does not offer a dataset choice; the dataset is selected through the API.
- Running the test: `uv run pytest tests/modules/v1/test_transferability.py -v`. To regenerate the side-by-side raw responses:
  `TRANSFER_EVIDENCE_DIR=<folder> uv run pytest tests/modules/v1/test_transferability.py -k side_by_side`.
